# ChronoSpatial (ZeroQuad)

**Розробка та порівняльний аналіз динамічних просторових індексів для систем реального часу**

Quadtree без жодної алокації пам'яті (zero-allocation) на основі пласких масивів для 2D-агентів, що постійно
рухаються. Як контрольні реалізації використано повний перебір (brute force) та класичне вказівникове
(об'єктне) quadtree. Проєкт містить набір бенчмарків BenchmarkDotNet, що вимірює всі три індекси, та
веб-симулятор на Blazor WebAssembly, який відображає «живий» індекс на HTML5 canvas.

**Ключовий результат (Chromium, AOT-збірка WebAssembly):**
**100 000 агентів при стабільних 60 FPS і такті симуляції 2,98 мс**, з яких 1,41 мс — оновлення просторового
індексу. 95,9 % агентів залишаються у своєму листі на кожному такті, дерево містить 12 801 вузол глибиною 8, а
пошук у радіусі, що повертає 828 об'єктів, коштує ~14 мкс.

**Ключовий результат (настільний CLR, `selftest 100000`):**
середній такт 3178,9 мкс, найгірший такт 5161,9 мкс і **0 байт алокацій за 600 тактів при 0 збірках Gen0**.

## Чому пласке quadtree

Класичне quadtree створює об'єкт вузла на кожен поділ і `List<T>` на кожен лист. При безперервному русі дерево
постійно перебудовується, тому ці алокації повторюються на кожному такті, і збирач сміття запускається в межах
бюджету кадру. При 100 тис. агентів і 60 Гц пауза GC — це пропущений кадр.

ZeroQuad повністю позбувається графа об'єктів:

| Класичний підхід | ZeroQuad |
|---|---|
| `class QuadNode` з 4 посиланнями | `struct QuadNode` (8 Б) в одному пласкому масиві, нащадки адресуються через `int` |
| `List<Entity>` на кожен лист | інтрузивний ланцюжок комірок, зв'язаних індексами, у спільному масиві |
| `new` при поділі, GC при злитті | вільні списки індексів повторно використовують групи вузлів і комірки |
| агенти як масив структур (AoS) | структура масивів (SoA: `float[] X, Y, VX, VY`), тож рух векторизується |
| видалення + повторна вставка кожного агента на кожному такті | dirty-check: повторно вставляються лише агенти, що справді покинули свій лист |
| негайне злиття при видаленні | відкладене амортизоване `Cleanup()` з гістерезисною «мертвою зоною» |

У результаті гаряча частина коду (`UpdateAll`, `QueryRange`) алокує **нуль** керованих байтів, що перевірено як
модульним тестом (різниця `GC.GetAllocatedBytesForCurrentThread()`), так і `[MemoryDiagnoser]`.

## Збирання та запуск

Потрібен .NET SDK 10.0.300 (див. `global.json`).

```powershell
dotnet build ZeroQuad.slnx -c Release
```

### Тести

> **SDK .NET 10 не може запустити ці тести через `dotnet test`.** Він завершується з помилкою
> *"Testing with VSTest target is no longer supported by Microsoft.Testing.Platform"*. Це особливість взаємодії
> SDK та раннера, а не дефект проєкту; її не виправляють ні `TestingPlatformDotnetTestSupport`, ні
> `UseMicrosoftTestingPlatformRunner`, ні видалення `Microsoft.NET.Test.Sdk`, ні кореневий `dotnet.config`.
> **Запускайте виконуваний файл тестів напряму:**

```powershell
dotnet build tests\SpatialEngine.Tests -c Release
tests\SpatialEngine.Tests\bin\Release\net10.0\SpatialEngine.Tests.exe
```

Найшвидший наскрізний доказ основного твердження. Код виходу 0 означає успіх.

```powershell
dotnet run --project bench\SpatialEngine.Benchmarks -c Release -- selftest 100000
```

```powershell
dotnet run --project bench\SpatialEngine.Benchmarks -c Release -- --filter *QueryBenchmarks*
dotnet run --project bench\SpatialEngine.Benchmarks -c Release -- --filter * --job short
```

### Веб-симулятор

```powershell
# розробка: швидкий старт, але працює на інтерпретаторі IL (див. нижче)
dotnet run --project src\SpatialEngine.Web -c Release

# репрезентативна продуктивність: AOT-компільований WebAssembly
dotnet workload install wasm-tools     # одноразово

```

**Завжди вимірюйте опубліковану збірку.** `dotnet run` віддає інтерпретовану збірку; той самий такт на 25 000
агентів коштує **76–104 мс в інтерпретаторі проти 0,7 мс після AOT-компіляції** — різниця ~100×, яка не має
жодного стосунку до самого індексу. Розмір опублікованого WebAssembly — близько 26 МБ.

## Індекс

### Розміщення в пам'яті

```csharp
struct QuadNode          // 8 Б: 8 вузлів на кеш-лінію
{
    public int FirstChild;   // гілка: індекс суцільної групи з 4 нащадків (NW, NE, SW, SE)
                             // лист:  голова ланцюжка елементів, -1 якщо порожній
    public int Count;        // >= 0 кількість елементів у листі, -1 гілка, -2 вільний
}
```

Нащадки виділяються **групою по чотири**, тож один `int` визначає всіх сусідів, а поділ зачіпає рівно один запис
вільного списку. Межі вузлів зберігаються в паралельному `Aabb[] _nodeBounds` (свідоме відхилення від їх
обчислення під час обходу: зберігання робить потактовий dirty-check читанням масиву за O(1) плюс одним
SIMD-порівнянням — це найгарячіша операція в системі). `_nodeMeta[].Parent` дозволяє агенту, що вийшов за межі,
піднятися *вгору* до найближчого предка, який його містить, замість спуску від кореня.

Належність елементів зберігається у **двозв'язному** ланцюжку 20-байтових записів `Cell`, тож від'єднання агента
відбувається за O(1) без сканування ланцюжка. `_agentLeaf[id]` та `_agentCell[id]` дають доступ до обох за O(1).

### Вільні списки індексів

`IndexFreeList<T>` зберігає вказівник «наступний вільний» звільнених комірок **всередині самого звільненого
елемента**, тож для повторного використання не потрібна допоміжна таблиця. Групи вузлів використовують
`Stride = 4`, комірки — `Stride = 1`. Масиви орендуються з `ArrayPool<T>.Shared` і ростуть подвоєнням, але
`EnsureCapacity` заздалегідь задає розмір усього під час створення та при зміні кількості агентів, тож
**жодного росту всередині такту не відбувається** (`GrowthCount` перевіряється на рівність 0 — самоперевірка на
100 тис. агентів показує 0).

> Ніколи не утримуйте `ref`, повернений `IndexFreeList`, через виклик `Allocate()` чи `EnsureCapacity()`: ріст
> перевиділяє внутрішній масив, і `ref` стає недійсним.

### Оновлення: dirty-check

```
leaf = _agentLeaf[i]
if (_nodeBounds[leaf].Contains(x[i], y[i])) continue;   // ~96 % агентів, одне SIMD-порівняння
Unlink(_agentCell[i]);
node = підйом через Parent, доки агент не міститься у вузлі;  // зазвичай 1–2 кроки
_agentLeaf[i] = InsertFrom(node, i);                     // спуск лише звідти
```

### Злиття

Злиття ніколи не відбувається всередині `Update`. `Cleanup()` запускається кожні `CleanupInterval` тактів і
згортає гілку, всі чотири нащадки якої є листами, що разом містять не більше ніж `NodeCapacity * MergeHysteresis`
(0,5) елементів. Коефіцієнт гістерезису менший за одиницю захищає від «пробуксовування»: інакше кластер, що
коливається біля межі місткості, ділився б і зливався на кожному такті.

### Запити

Дві форми API, обидві без алокацій:

```csharp
int  QueryRange(in Aabb box, Span<int> results);     // повертає кількість, повідомляє про усічення
int  QueryRange(in Circle c, Span<int> results);     // широка фаза AABB, вузька — квадрат відстані
void QueryRange<TVisitor>(in Aabb box, ref TVisitor visitor)
     where TVisitor : struct, IQueryVisitor, allows ref struct;   // generic-параметри ref struct з C# 13
```

Обхід ітеративний, по заздалегідь орендованому стеку `int[]` — ніколи не рекурсивний і ніколи не `Stack<T>`.

## Симуляція

`AgentWorld` зберігає стан агентів як структуру масивів, тож `BrownianWalk` може загасати, додавати шум,
обмежувати, інтегрувати, відбивати та обрізати за межами цілий блок `Vector<float>` за раз. `GravityWellField`
додає до 16 атракторів, що притягують агентів до точки (саме вони моделюють зони аномального скупчення об'єктів).

Два проєктні рішення варто виділити, бо обидва були помилками, які виявили тести:

**Безстанний ГВЧ.** Станний ГВЧ на кожну лінію робить кожне значення залежним від кількості попередніх, тож
розбиття рою між потоками непомітно змінювало симуляцію й робило будь-яке порівняння послідовного та
паралельного режимів безглуздим. Його замінено на `CounterRandom` — безстанний хеш lowbias32 від
`(seed, sequence, stream, agentIndex)`. Він коштує два множення і три зсуви на значення та робить послідовний і
паралельний запуски **побітово ідентичними**.

**Лінійне згасання гравітації.** Обернено-квадратичний закон зосереджує майже весь ефект у крихітному ядрі, тож
на демонстраційних відстанях повзунок «сили» нічого помітно не змінював. Тепер поле використовує лінійний спад
`max(0, 1 - dist/Radius)`: `Strength` буквально означає пікове прискорення в центрі, а сила неперервно спадає
точно до нуля на радіусі, тож агенти, що перетинають межу, не відчувають розриву.

`SimulationHost` працює з фіксованим кроком і акумулятором. Він обмежує вхідну дельту значенням
`step * MaxCatchUpTicks` (фонова вкладка браузера передає багатосекундні дельти) і відкидає залишок, більший за
один крок, тож борг симуляції не може накопичитися у «спіраль смерті».

## Веб-симулятор

Дерево рендерингу Blazor **не** бере участі в циклі анімації. JavaScript керує `requestAnimationFrame` і викликає
.NET; .NET повертає сирі представлення пам'яті купи WebAssembly.

### Бінарний протокол

```csharp
[JSImport("renderFrame", "renderer")]
internal static partial void RenderFrame(
    [JSMarshalAs<JSType.MemoryView>] ArraySegment<byte> rgba,    // кадровий буфер W*H*4
    [JSMarshalAs<JSType.MemoryView>] ArraySegment<byte> rects,   // float32 прямокутники (minX, minY, w, h)
    int rectCount,
    bool wireframeChanged,
    bool showGrid,
    [JSMarshalAs<JSType.MemoryView>] ArraySegment<byte> stats);  // упакований float32[12]
```

- **Агенти.** .NET растеризує їх самостійно: `FrameBuffer.SplatAll` — це обмеження, індекс і 4-байтовий запис на
  агента. JavaScript виконує один `putImageData`. Це **одне копіювання пам'яті на кадр незалежно від кількості
  агентів** — єдина схема, що чисто масштабується до 100 тис.+. Результати запиту наносяться другим проходом
  іншим кольором.
- **Каркас дерева.** `FlatQuadtree.CollectNodeBounds` записує прямокутники `(minX, minY, width, height)` у
  заздалегідь орендований буфер; JavaScript будує один `Path2D` і обводить його один раз. Каркас
  перебудовується **лише при зміні `TopologyVersion`**, а не кожного кадру.
- **Телеметрія.** Упакований `float32[12]`, який JavaScript записує **безпосередньо у текстові вузли DOM** з
  частотою 4 Гц. Читання статистики ніколи не спричиняє повторного рендерингу Blazor, тож інтерфейс не може
  загальмувати кадр.

Виклики JavaScript → .NET використовують делегати, маршалізовані як `JSType.Function`, оскільки їхні сигнатури
перевіряються компілятором. Згенерований інтероп маршалізує **щонайбільше три аргументи на делегат**, тому
позиція вказівника та його активація — це два окремі зворотні виклики. Еквівалентні точки входу `[JSExport]`
є в `SimulationBridge` для налагодження з консолі, але симулятор від них не залежить.

### Елементи керування

Пауза/продовження, створення «гарячої точки», очищення атракторів, кількість агентів (1 тис.–150 тис.), частота
тактів (20–120 Гц), `MaxDepth` (2–11), `NodeCapacity` (2–64), показ сітки, сітка лише листів. Перетягування на
полотні задає радіус пошуку, прокручування змінює його розмір, подвійне клацання — очищає.

| Кластерний | 1 % | 358 мкс | 160 мкс | — | — |
| Рівномірний | 5 % | 4129 мкс | — | 4934 мкс | 1,2× |

Усі три індекси алокують 0 Б на шляху запиту.

## Висновки

**Пласке дерево виграє за алокаціями та затримкою оновлення, а не за локальністю запитів.** Об'єктне дерево
стабільно дещо *швидше на запитах* — при кластерному розподілі й площі 1 % воно більш ніж удвічі швидше (160 мкс
проти 358 мкс). Причина чесна і структурна: `OopQuadtree` зберігає елементи листа суцільно в `List`, що дуже
зручно для префетчера, тоді як пласке дерево проходить ланцюжком комірок, зв'язаних індексами, які можуть бути
розкидані по пулу. Пласке дерево платить цю ціну локальності за від'єднання за O(1) та нуль алокацій. Для
*динамічного* індексу — який оновлюється значно частіше, ніж опитується, — це правильний компроміс, і бенчмарк
оновлення показує чому. Для переважно статичного індексу з інтенсивними запитами кращим вибором була б суцільна
схема кошиків.

**Селективність вирішує все.** Перевага quadtree зникає, коли запит охоплює більшу частину світу: 66× при 0,1 %
кластерного світу, 8,3× при 0,1 % рівномірного, 1,2× при 5 % рівномірного. Приблизно після 10 % площі світу
SIMD-перебір стає конкурентоспроможним, бо дерево все одно відвідує більшість листів і ще й платить за обхід.

**Рекомендації щодо параметрів.** `MaxDepth 8` / `NodeCapacity 16` — найкраще універсальне налаштування для
100 тис. агентів у симуляторі; воно дає ~12,8 тис. вузлів і 95,9 % влучань dirty-check. Менша місткість або
більша глибина ділять простір агресивніше, що сильніше відсікає запити, але збільшує кількість поділів/злиттів і
частку агентів, які покидають свій лист на кожному такті. Неглибокі дерева (`MaxDepth 4`) при кластеризації
вироджуються до перебору, бо обмеження глибини змушує листи містити значно більше ніж `NodeCapacity` елементів.

**Кластеризація допомагає дереву і шкодить базовому варіанту.** Кожна «гаряча точка» робить перебір відносно
гіршим (він усе одно сканує все), а дерево — відносно кращим (воно відсікає цілі порожні області). Тож
гравітаційні колодязі в симуляторі — не прикраса, а саме той несприятливий випадок, що робить порівняння
змістовним.

**AOT для WebAssembly обов'язковий.** Інтерпретована збірка виконує той самий такт ~100× повільніше. Будь-яке
твердження про продуктивність збірки Blazor WASM без AOT-публікації не має сенсу.

**Економічний та екологічний ефект.** Нуль алокацій і відсутність пауз GC означають передбачувану затримку такту:
100 тис. рухомих об'єктів обробляються за ~3 мс на одному ядрі, тобто піковий трафік можна обслуговувати на
менших і дешевших інстансах, а менша кількість процесорного часу на такт безпосередньо зменшує енергоспоживання.

## Відомі обмеження

- **Лише точкові агенти.** Агенти не мають розміру, тож кожен належить рівно одному листу. Агенти з розміром
  потребували б належності до кількох листів і проходу дедуплікації при запиті.
- **Фіксовані межі світу.** Кореневий AABB задається при створенні й ніколи не розширюється; моделі руху
  відбивають агентів від межі.
- **Паралельний шлях руху алокує.** `Parallel.For` сам по собі алокує пам'ять, тому `UseParallelMovement` за
  замовчуванням `false`, і гарантія нуля алокацій вимірюється на послідовному шляху. WebAssembly тут у будь-якому
  разі однопотоковий.
- **Гранулярність таймера браузера.** Без cross-origin isolation Chromium округлює високоточний годинник до
  100 мкс, тож одиничне вимірювання менше 100 мкс читається як 0 або 100. Показані значення експоненційно
  згладжуються між кадрами, щоб відновити змістовне середнє з квантованих вибірок; настільні бенчмарки цієї
  проблеми не мають.
- **Апаратні лічильники** (промахи кешу, помилки передбачення переходів) потребують підвищених прав для ETW;
  конфігурація бенчмарків мовчки відключає цей діагностувальник, якщо він недоступний.
